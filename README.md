# AvionixDesigner

AvionixDesigner — редактор кадров на C++ и Qt для графического контроллера на базе ПЛИС. Приложение позволяет собирать интерфейс из объектов, редактировать их параметры и сохранять кадр в XML со схемами и порядком полей, необходимыми контроллеру.

## Возможности

- Прямоугольники, штриховые линии, ленточные шкалы, авиагоризонт, текст и импорт изображений.
- Выделение, группировка, выравнивание, изменение порядка объектов, отмена и повтор действий.
- Сетка и привязки к холсту, сетке и другим объектам.
- Область 3D-вида и панель позиционирования самолета: координаты X/Y, курс, высота, блок тангажа (yscreen) и автопилот.
- Подготовка пакетов ПЛИС, сохранение бинарных данных, передача по UART и встроенный симулятор.
- Загрузка и сохранение XML, подготовка растровых масок и шрифтов для ПЛИС.

## Сборка

Требования:

- CMake 3.19 или новее.
- Компилятор с поддержкой C++17.
- Qt 6.5 или новее с модулями `Core`, `Widgets`, `Xml`, `Svg` и `SerialPort`.
- NSIS — для создания установщика Windows через CPack.

Локальная сборка:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --config Debug --parallel
```

Если CMake не находит Qt, укажите каталог установленного комплекта Qt через `-DCMAKE_PREFIX_PATH=/path/to/Qt/kit` при конфигурации.

Приложение можно запустить из Qt Creator, открыв `CMakeLists.txt`, либо из каталога сборки:

- macOS: `build/AvionixDesigner.app`.
- Linux: `build/AvionixDesigner`.
- Windows с Visual Studio: `build/Debug/AvionixDesigner.exe`.

Для сборки установочного пакета:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release --parallel
cmake --build build --config Release --target package
```

CPack создает установщик NSIS для Windows, DMG для macOS или архив TGZ для Linux. Сценарий [Windows Release](.github/workflows/windows-release.yml) собирает и публикует установщик Windows; версию он берет из `CMakeLists.txt`.

## Работа с 3D-видом

Добавьте объект «3D вид» из библиотеки объектов, чтобы включить панель позиционирования самолета. Область 3D-вида закрепляется у левого или правого края холста; сторона выбирается в свойстве «Положение».

Координаты X и Y задаются в **точках карты от 0 до 8191**, с шагом **1/64 точки**. По эталонному [All_together.py](checks/protocol/All_together.py) одна точка равна 32 м, один raw-шаг координаты — 0,5 м. X увеличивается вправо, Y — вверх. Весь диапазон показан на одной области без переключения квадратов. При выходе за край самолет переходит на противоположную сторону, сохраняя остаток перемещения; автопилот продолжает работать. Переход действует по обеим осям, в том числе по диагонали. Панель и объект 3D-вида отображают одно состояние модели.

Курс соответствует формулам Python: **0° — +X, 90° — +Y**. Поле допускает дробные градусы, шаг ввода — 0,05°. Автопилот сейчас использует 1400 км/ч и фактически прошедшее время, обновляя положение примерно раз в 16 мс. Дробное перемещение сохраняется и не округляется до целых точек.

Высота вводится с шагом **0,25 м** в рабочем диапазоне **0…16383,75 м**. Колесо на ползунке меняет высоту на 0,25 м, Shift + колесо — на 10 м, Page Up/Page Down — на 100 м. Отрицательные высоты из XML сохраняются, поле ввода расширяется до импортированного значения. Ползунок остается в положительном диапазоне.

Блок в панели называется **«Тангаж»** для удобства управления, но поле остается непосредственно `yscreen`, без преобразования в градусы: 0…1023. В XML, пакетах и программной модели используется имя `yscreen`. Новый 3D-вид получает настройки рабочего примера Python: высота 16000 м, курс 45°, `yscreen = 1023`. Старое XML-поле `pitch` принимается как прежнее имя тех же 10 сырых битов; при сохранении используется `yscreen`.

Клавиши работают при фокусе в панели позиционирования, например после щелчка по экрану или крутилке. Числовые поля сохраняют обычное редактирование текста. Полный список также доступен в **Настройки → Горячие клавиши**.

| Управление | Точный шаг | С зажатым Shift |
| --- | --- | --- |
| ← / → | Курс ±0,05° | ±1° |
| ↑ / ↓ | Тангаж ±1 единица yscreen | ±10 |
| + / −, также = | Высота ±0,25 м | ±10 м |

На основной клавиатуре «=» позволяет набирать высоту точным шагом, Shift+= — ускоренным. Клавиша «+» цифрового блока работает напрямую. Shift ускоряет также колесо регуляторов и кнопки тангажа.

Экран панели всегда квадратный. Размер содержимого панели ограничен диапазоном 800×360…1600×900 логических пикселей; элементы управления масштабируются по доступному месту. Компактные панели библиотеки, параметров холста и ПЛИС переносят кнопки на новые строки, а при недостаточной высоте показывают прокрутку. Вертикальная панель действий также прокручивается, не увеличивая минимальную высоту всего редактора.

## UART

Порт открыт на весь сеанс. В окне запуска отдельно задаются **скорость загрузки** (по умолчанию 921600 бод), **скорость управления** (115200 бод) и интервал отправки (20 мс).

1. Один раз отправляются начальный байт `00`, параметры и маски сцены, затем команда стороны 3D-вида.
2. Перед сменой скорости отправитель дожидается завершения передачи. Все операции порта выполняются в отдельном потоке и не блокируют движение самолета и интерфейс.
3. Дальше отправляются короткие пакеты положения 3D-вида. Маски повторно загружаются при изменении сцены, а смена только стороны 3D-вида посылает только команду стороны. При движении не пересобираются шрифты и маски.
4. Очередь содержит только последнее ожидающее положение. Старые положения не накапливаются за медленным UART.

Интервал **0** означает отсутствие дополнительной паузы после готовности передатчика. Положительное значение задает минимальное время между началами пакетов положения. Для 8N1 пакет положения из 30 байт при 115200 бод занимает минимум около 2,60 мс; реальная частота зависит от драйвера и USB-UART. Режим 0 не означает мгновенную передачу.

## XML для ПЛИС

Сохранение формирует XML в кодировке Windows-1251: `<project name="…" width="…" height="…" bgcolor="#BBGGRR">`, затем `<parameters>` с используемыми схемами и `<objects>` с объектами. Названия тегов и полей чувствительны к регистру; в частности, `RibonScale`, `Enable` и `Color` записываются именно так.

При импорте поля читаются по схемам исходного файла. При сохранении и `<parameters>`, и `<init>` используют актуальный [реестр схем](src/schema/FpgaSchemaRegistry.cpp). Документация аппаратных модулей и Verilog находятся в [docs](docs/).

Общие правила для таблиц ниже:

- Биты нумеруются от младшего, диапазоны `[старший:младший]` включают обе границы. Все текущие слова `<init>` имеют 150 бит и 38 HEX-символов; два неиспользуемых старших бита HEX-контейнера равны нулю.
- `uN` — беззнаковое целое от 0 до `2^N − 1`; `sN` — знаковое целое в дополнительном коде от `−2^(N−1)` до `2^(N−1) − 1`. Отрицательные значения записываются младшими N битами дополнительного кода.
- Дробные значения используют **фиксированную точку**, а не IEEE 754: число умножается на масштаб и округляется до целого. Для 3D-вида ровная половина округляется к четному, как в Python `round`. Например, высота −0,25 м — это raw = −1, в 17 битах `0x1FFFF`.
- Цвет — `u24` в порядке BGR: `[23:16]` — B, `[15:8]` — G, `[7:0]` — R. Например, RGB `#123456` упаковывается как `0x563412`. Прозрачность хранится отдельно.
- `padding` — резерв. У новых слов он нулевой; 3D-вид сохраняет импортированные резервные биты.
- Пиксельные поля геометрии целочисленные. Для 12-битных беззнаковых координат предел — 4095; для знаковых 12-битных смещений — −2048…2047. Пределы полей следует учитывать при отладке больших объектов: не все редакторские операции ограничивают геометрию аппаратным диапазоном.

Объекты без маски содержат только `<init>`. `<staticgroup>`, `<rotationobject>` и `<font>` дополнительно содержат `<data>` с десятичными уровнями маски 0…7 через запятую: 0 — прозрачный пиксель, 7 — максимальная непрозрачность. В XML маски идут построчно, слева направо и сверху вниз; переупаковку в аппаратные блоки выполняет компилятор пакетов. У `<text>` в `<data>` находятся коды символов, а не пиксельная маска.

### 3D-вид — `<layer3d>`

Один `<init>`, без `<data>`. В XML размещается первым. В BIN/UART после обычной сцены идут два пакета типа `0x06`: сначала сторона (1 байт: left = 1, right = 0), затем положение (19 байт little-endian). Константы формата — [Layer3dFormat.h](src/fpga/model/Layer3dFormat.h).

| Поле | Биты | Формат | Назначение |
| --- | --- | --- | --- |
| `x` | `[18:0]` | u19 / 64 | X, 13 целых и 6 дробных битов; точки карты 0…8191 |
| `y` | `[37:19]` | u19 / 64 | Y, 13 целых и 6 дробных битов; точки карты 0…8191 |
| `course` | `[56:38]` | u19 × 360 / 2^19 | Курс в градусах: 0 ≤ угол < 360°; полный оборот равен 524288 единицам, шаг raw ≈ 0,000686646° |
| `height` | `[73:57]` | s17 / 4 | Высота −16384…16383,75 м, шаг 0,25 м |
| `yscreen` | `[83:74]` | u10 | Y экрана 0…1023, по умолчанию 1023; это не угол в градусах |
| `padding` | `[149:84]` | u66 | Резерв |

Поле высоты не теряет дробные биты при чтении, редактировании, отмене/повторе и сохранении. Дробные части координат и курса сохраняются при редактировании других полей. Сторона размещения 3D-вида сохраняется комментарием XML и не занимает биты аппаратного слова.

### Прямоугольник с прозрачностью — `<rectangle_a>`

Один `<init>`, без `<data>`. Используется для прямоугольника с явной или частичной прозрачностью. Значение `alph = 0` означает 1/8 непрозрачности, а не полностью прозрачную заливку; отдельного значения нулевой непрозрачности в этом поле нет.

| Поле | Биты | Формат | Назначение |
| --- | --- | --- | --- |
| `enb` | `[0:0]` | u1 | Разрешение отображения |
| `color` | `[24:1]` | u24, BGR | Цвет заливки |
| `colorb` | `[48:25]` | u24, BGR | Цвет рамки |
| `alph` | `[51:49]` | u3 | Непрозрачность: аппаратный коэффициент `(alph + 1) / 8`, от 1/8 до 1 |
| `x0` | `[63:52]` | u12 | X левого верхнего угла |
| `y0` | `[75:64]` | u12 | Y левого верхнего угла |
| `w` | `[87:76]` | u12 | Ширина, пиксели |
| `h` | `[99:88]` | u12 | Высота, пиксели |
| `a` | `[111:100]` | u12 | Толщина рамки, пиксели |
| `padding` | `[149:112]` | u38 | Резерв |

### Поворачиваемая маска — `<rotationobject>`

Один или несколько `<init index="…">` для аппаратных слоев и общий `<data width="…" height="…">`. Правая и нижняя границы определяют размер разностями `right − left`, `bottom − top`. Компилятор пакетов разбивает маску на тайлы 8×8 с дополнительной строкой и столбцом для интерполяции. Значения sin/cos ±1 записываются как ±65536 и помещаются в s18.

| Поле | Биты | Формат | Назначение |
| --- | --- | --- | --- |
| `enb` | `[0:0]` | u1 | Разрешение слоя |
| `color` | `[24:1]` | u24, BGR | Цвет маски |
| `xrot` | `[36:25]` | u12 | X центра вращения на экране |
| `yrot` | `[48:37]` | u12 | Y центра вращения на экране |
| `top` | `[60:49]` | s12 | Верхняя граница относительно центра вращения |
| `left` | `[72:61]` | s12 | Левая граница относительно центра вращения |
| `bottom` | `[84:73]` | s12 | Нижняя граница относительно центра вращения |
| `right` | `[96:85]` | s12 | Правая граница относительно центра вращения |
| `sq` | `[104:97]` | u8 | Количество тайлов по X: `ceil((right − left) / 8)`, до 255 |
| `sin` | `[122:105]` | s18 / 65536 | Синус угла поворота, 16 дробных битов |
| `cos` | `[140:123]` | s18 / 65536 | Косинус угла поворота, 16 дробных битов |
| `padding` | `[149:141]` | u9 | Резерв |

### Статическая маска / группа состояний — `<staticgroup>`

Один `<init index="…">` на состояние и один общий `<data>`. Атрибут `nomber` сохраняется с таким написанием. Пиксель `(x, y)` состояния находится в памяти по индексу `addr + y × w + x`; резервная/неиспользуемая память заполняется нулями. Не путать аппаратный объект с редакторской группировкой выделенных объектов.

| Поле | Биты | Формат | Назначение |
| --- | --- | --- | --- |
| `enb` | `[0:0]` | u1 | Разрешение состояния |
| `color` | `[24:1]` | u24, BGR | Цвет состояния |
| `x` | `[36:25]` | u12 | X левого верхнего угла |
| `y` | `[48:37]` | u12 | Y левого верхнего угла |
| `w` | `[60:49]` | u12 | Ширина маски, пиксели |
| `h` | `[72:61]` | u12 | Высота маски, пиксели |
| `addr` | `[88:73]` | u16 | Смещение маски в общей памяти, в элементах маски |
| `padding` | `[149:89]` | u61 | Резерв |

### Штриховая линия — `<dashed_line>`

Один `<init>`, без `<data>`. `dt` вычисляется по расстоянию между концами с округлением до целого. Значение +256 не помещается в s9: максимально положительный коэффициент равен 255/256. Это дает небольшую погрешность направления/длины, но не меняет знак направления. Длины больше 4095 не представимы положительным s13.

| Поле | Биты | Формат | Назначение |
| --- | --- | --- | --- |
| `Enable` | `[0:0]` | u1 | Разрешение отображения |
| `Color` | `[24:1]` | u24, BGR | Цвет линии |
| `xo` | `[36:25]` | u12 | X начала линии |
| `yo` | `[48:37]` | u12 | Y начала линии |
| `dt` | `[61:49]` | s13 | Длина линии; для прямого направления используются положительные значения 1…4095 |
| `a` | `[70:62]` | s9 / 256 | Коэффициент направления X: `round((x1 − x0) / dt × 256)`, ограничен −256…255 |
| `b` | `[79:71]` | s9 / 256 | Коэффициент направления Y: `round((y1 − y0) / dt × 256)`, ограничен −256…255 |
| `StepPow` | `[82:80]` | u3 | Период штриха равен `2^(raw + 1)`, то есть 2…256 пикселей |
| `Length` | `[90:83]` | u8 | Длина штриха минус 1: 1…256 пикселей |
| `Phase` | `[98:91]` | u8 | Фаза штриха, пиксели |
| `Width` | `[102:99]` | u4 | Толщина линии минус 1: 1…16 пикселей |
| `padding` | `[149:103]` | u47 | Резерв |

| Поле | Биты | Формат | Назначение |
| --- | --- | --- | --- |

| `color` | `[24:1]` | u24, BGR | Цвет рисок |
| `left` | `[36:25]` | u12 | Левая граница |
| `right` | `[48:37]` | u12 | Правая граница |
| `top` | `[60:49]` | u12 | Верхняя граница |
| `bottom` | `[72:61]` | u12 | Нижняя граница |
| `width` | `[76:73]` | u4 | Толщина риски минус 1: raw 0…15 означает 1…16 пикселей |
| `period` | `[84:77]` | u8 | Период рисок, в редакторе 1…255 пикселей |
| `ystart` | `[96:85]` | u12 | Начальная Y-координата последовательности рисок |
| `padding` | `[149:97]` | u53 | Резерв |

### Ресурс шрифта — `<font>`

Один `<init>` на символ и общий `<data>` с масками. Атрибуты `<font>`: `index`, `name`, `size`, `count`, `volume`; `volume` задается в битах как число элементов маски × 3. У `<init>` есть `index`, `literal`, `code`. Дополнительные `<kerning left="…" right="…" delta="…">` задают знаковую поправку расстояния между парой символов. Эти атрибуты и элементы не занимают биты init.

| Поле | Биты | Формат | Назначение |
| --- | --- | --- | --- |
| `enb` | `[0:0]` | u1 | Разрешение глифа |
| `code` | `[16:1]` | u16 | Код символа UTF-16 |
| `w` | `[28:17]` | u12 | Ширина маски глифа |
| `h` | `[40:29]` | u12 | Высота маски глифа |
| `advance` | `[52:41]` | u12 | Сдвиг пера к следующему символу |
| `bearing_x` | `[64:53]` | s12 | Смещение маски по X относительно пера |
| `bearing_y` | `[76:65]` | s12 | Смещение маски по Y относительно базовой линии |
| `ascent` | `[88:77]` | u12 | Высота над базовой линией |
| `descent` | `[100:89]` | u12 | Глубина под базовой линией |
| `offset` | `[124:101]` | u24 | Начальный индекс маски глифа в общем data, в элементах маски |
| `mask_size` | `[136:125]` | u12 | Количество элементов маски глифа, обычно w × h; максимум 4095 |
| `font_index` | `[144:137]` | u8 | Индекс шрифта, 0…255 |
| `padding` | `[149:145]` | u5 | Резерв |

### Текстовая строка — `<text>`

Один `<init>` на редакторский текстовый объект и `<data>` со списком десятичных кодов UTF-16 через запятую. В текущем экспорте `char_offset = 0`. Атрибут `text` у `<init>` хранит читаемую строку для редактора; аппаратный вывод использует коды data и маски выбранного font. Позиционирование глифов учитывает advance, bearing и kerning.

| Поле | Биты | Формат | Назначение |
| --- | --- | --- | --- |
| `enb` | `[0:0]` | u1 | Разрешение отображения |
| `color` | `[24:1]` | u24, BGR | Цвет текста |
| `x` | `[36:25]` | u12 | X начала строки |
| `y` | `[48:37]` | u12 | Y начала строки |
| `font_index` | `[56:49]` | u8 | Ссылка на индекс ресурса font |
| `char_offset` | `[72:57]` | u16 | Индекс начала строки в списке кодов data |
| `char_count` | `[84:73]` | u12 | Число кодов символов строки, до 4095 |
| `padding` | `[149:85]` | u65 | Резерв |

### Изображения и редакторские группы

`ImageObject` не сохраняется отдельным аппаратным тегом `<image>`. Изображение раскладывается на цветовые маски: без поворота — в `<staticgroup>`, с поворотом — в `<rotationobject>`. Для них действуют описанные выше поля и ограничения памяти. Редакторские группы служат для совместного выделения и управления объектами; собственных init/data у них нет.

## Проверка протокола без ПЛИС

Подробности и границы проверки — в [checks/protocol/README.md](checks/protocol/README.md). Нужны Qt Test и Python 3.10+. Эталон `All_together.py` и скрипт сравнения `verify_fpga_packets.py` находятся вместе в `checks/protocol/`; весь каталог должен попасть в коммит вместе с изменениями приложения. Для сравнения не нужны pyserial, keyboard, numpy или OpenCV: инструмент исполняет выбранные функции упаковки и XML-загрузчика с перехватом байтов вместо реального порта.

```bash
cmake -S . -B build -DAVIONIX_BUILD_TESTS=ON -DCMAKE_BUILD_TYPE=Debug
cmake --build build --config Debug --parallel
ctest --test-dir build -C Debug --output-on-failure
```

Проверки создают свежие `reference-left.xml` и `reference-right.xml` в `build/verification/`, прогоняют каждый файл через Python и реальное приложение и сравнивают BIN целиком. Там же остаются пары `python-*.bin`, `editor-*.bin` и контрольные векторы положения. Готовые BIN не включаются в исходники.

Для отдельного экспорта без открытия окна:

```bash
# macOS; на Windows используйте build/Debug/AvionixDesigner.exe
build/AvionixDesigner.app/Contents/MacOS/AvionixDesigner --export-bin build/verification/reference-left.xml build/frame.bin
```

`--export-xml input.xml output.xml` сохраняет канонический XML тем же путем, который использует редактор. Обе команды работают без подключения UART и используют временный профиль настроек. При обычном запуске редактор использует прежнее хранилище настроек пользователя; для отдельного диагностического профиля можно явно задать путь к INI-файлу в переменной `AVIONIX_SETTINGS_FILE`.

## Выпуск новой версии

Для следующего выпуска подготовлена версия **1.0.7** в `CMakeLists.txt`.

1. Для каждого нового выпуска задайте новый `VERSION` в строке `project(AvionixDesigner VERSION …)`.
2. Соберите и проверьте приложение, затем закоммитьте изменения и отправьте их в `main` командой `git push origin main` (либо объедините pull request в `main`).
3. На GitHub откройте **Actions → Windows Release** и дождитесь успешного завершения. Workflow установит Qt и NSIS, соберет приложение, выполнит проверки протокола и только после их успеха соберет установщик.
4. Готовый файл **AvionixDesigner-1.0.7-windows-x64.exe** появится в **Releases → v1.0.7 → Assets**, а также среди артефактов запуска Actions. Тег и релиз создаются автоматически; вручную создавать тег не требуется. При провале проверок установщик не публикуется, а диагностические файлы сохраняются в артефакте `protocol-diagnostics`.

Сборку также можно запустить вручную через **Run workflow** для ветки `main`. Версии должны быть уникальными: существующий workflow при повторе версии заменяет файл установщика в том же релизе, но существующий тег не переносит на новый коммит. Поэтому для нового набора изменений увеличивайте версию, а не переиспользуйте прежнюю.
